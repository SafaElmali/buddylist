# Project managers

A project can have a **manager**: a contact using Claude, Codex, Gemini, OpenCode or Hermes that oversees the conversations working on it that you put under it, each in a worktree of its own. It knows what the project is building, from the PRDs, tickets, Slack discussions and designs you point it to. Each time one of them changes files, it looks at the changes against all of that, and tells that conversation what has to change. A project can have [several](#several-managers), each over conversations of its own, such as one for a release and one for the features.

**Adding one.** Right-click the project in the contact list and choose **Add a manager...**. Or choose **Contacts > Add a manager...**, also found by typing "manager", "oversee" or "PM" in the palette (**⌘K**), and pick the project. A repository no contact works in yet can have one too: its **Project** ends with **Another repository...**, which asks for the folder, and with no project to offer, it asks for one before the dialog opens. The manager is then the project's first contact, and you add the conversations it oversees with the + on its row. The palette lists each project's **Manager** page of Settings too. The dialog asks for little: its **Service** and **Model**, Claude with Sonnet to begin with, and a **First source**, such as the link to the PRD, which can be left empty. **Add manager** adds a contact named after the project, such as **tagsapp manager**, to the project's section of your contact list, and opens its conversation. It leads that section: it is listed first, before pinned contacts, with a star on its buddy. Its row has no manager tint or accent strip; highlighting marks a selected row or the conversation open in that window. When it has nothing else to say its row tells how many conversations it oversees. The ones under it are listed under it, whoever started them, and the count at the end of its row says how many: click the arrow before its buddy, or the count, to hide or show them. Tab reaches the arrow, and Left and Right still fold and unfold the selected row. Folded conversations stay folded across reloads and restarts, in both contact lists. One that is waiting for you, a favorite or offline stays in that section. Turned off, it is a contact like any other. It works in the main checkout, and it changes no files itself. A new manager starts with no conversations under it: put the ones it should oversee under it (see below). Once a project has one, its right-click menu has **Manager settings...**, which opens its page in Settings, **Turn off manager** and **Add another manager...** instead. Only a git repository can have one.

Adding a manager is complete on its own, including when it has **zero workers**. It does not open Add a Contact, create a worktree or request a worker. Add workers separately with **+** or **Add a Contact**, or ask the manager to start one later. Choosing standalone **Add a manager...** while an unfinished Add Contact form is open cancels that contact flow, so it cannot reappear after the manager joins.

**Stopping its current turn.** Open **Agents** from the side pane's **+**, then press **Stop** on the manager's row. It works with a manager alone too. While interruption is pending it says **Stopping…**; when the manager is idle, Stop is unavailable. This is the same Stop as in the message box: with guests, it stops the current round in this conversation, including guests and queued replies. Separate workers and other managers keep going. The manager stays assigned and enabled, with its brief, sources, history and read-only restrictions intact. Worker notes already waiting or arriving afterward stay visible and wait for your next message before the manager reads them. Stop is a current-session interruption; use **Turn off manager** when you want to disable project management. Pause, resume and remove retain their separate meanings.

**Continue stopped workers with another service.** Right-click a manager in either contact list, or open its **Team** menu, and choose **Continue workers with...**. Select eligible conversations, then choose a service, model and effort. Each worker continues in its existing folder and conversation, with no broader permissions, while its previous agent stays paused. Results are reported per worker, with a retry for failures. The manager itself and **New workers use** are unchanged. See [Continuing with another provider](accounts.md#continuing-with-another-provider).

**Putting a conversation under it.** A manager oversees the conversations under it, and no others:

- **Add a Contact** on a git repository has **Under**: pick one of its managers, or leave it at **No manager**, which is where the project's **+** starts it. Where a manager's **scope** takes the new contact's branch, or its issue or pull request, Under starts at that manager instead, and says so: see **Scope** below. Pick another and it stays as you picked. On a project with no manager yet, Under ends with **Add a manager...**, and once it has one, with **Add another manager...**: either opens the same dialog as the project's menu, and the manager it adds is picked in Under, so **Add** puts the new contact under it. **Add manager** returns to that same contact draft, keeping its fields and selecting the new manager. It never submits the contact: press **Add** separately when ready. **Cancel** in the manager dialog leaves Under as it was; cancelling Add Contact leaves the manager in place without creating a worker. Picking another project in **Works on** shows that project's managers. This computer and a folder outside a git repository have no Under.
- The **+** at the end of a manager's row adds a contact under that manager: Add a Contact opens with **Under** set to it.
- **Assign to manager...**, in a conversation's right-click menu, puts it under one of the project's managers, or under **No manager**. Each choice says how many conversations that manager oversees.
- **Assign conversations...**, in a manager's right-click menu or its own window's **Team** menu, puts many under it at once. It lists the project's conversations, each with where it is now, such as _Under release manager_ or _No manager_. The ones under it are ticked. Tick the ones to put under it, or **All**, and untick the ones to take out from under it, which go under no manager.
- **Drag** a conversation's row onto a manager's row to put it under that manager, or onto its project's line to take it out from under any. The row you can drop on is outlined.
- A conversation a manager [starts](started-conversations.md) is under that manager, and one that a conversation under a manager starts is under the same manager.
- A manager turned off keeps the conversations under it, and nobody oversees them until it is on again. Turning it on never takes the ones you left under no manager.
- A conversation whose folder you move to another project, with **Edit contact...**, is under no manager there. One whose manager is deleted is under none.
- Updating to this version put every conversation of a project under the manager it had, once, so nothing changed for them.

**Or in Settings.** Open **Settings**, pick the project, and go to its **Manager** page. Turn on **A manager oversees this project**: the bar at the bottom says **Manager joined tagsapp.**, and **Open its conversation**, under the switch, opens it.

## Several managers

With many conversations on one project, such as a release, some research and a few features at once, one manager hears of all of them, and unrelated work ends up in one brief. Give each part a manager of its own instead:

- **Adding one.** Right-click the project and choose **Add another manager...**, or press it on the project's **Manager** page in Settings. Give it a **Name**, such as _release manager_, a **Scope** if you like, a **Service**, **Model** and a **First source**. It joins the project's section with its own row, and starts with no conversations: put them under it as above.
- **Starting from another.** **Start from** picks what it starts with: _shop manager's settings and brief_, which it starts with, _shop manager's settings_, or **Nothing: a fresh start**. With several managers, each has both. Its settings are a copy of that manager's sources, checks, own checks and instructions, and of all else it is set up with, but whether it is on and its scope: the scope is what tells them apart. **Service** and **Model** start out as that manager's, and the ones you pick are used. A **First source** it hasn't got is added to the copied ones. The brief is a copy too, as it is when you add the manager: each edits its own from then on. A manager that starts with a copied brief is told whose it is, so it looks at which conversations are under it before it goes by what the brief says of who is on what.
- **Each on its own.** Every manager has its own model, scope, sources, brief, checks and instructions. With two or more, the project's **Manager** page in Settings lists them, each with whether it is on, its model, how many conversations are under it and its scope: click one to set it up under its line, one at a time. **Manager settings...**, in a manager's own window or its right-click menu and **⋯** in the contact list and the list beside a conversation, opens the page on it. The project's **Overview** says how many managers it has and how many conversations are under them, such as _2 managers · 5 conversations_.
- **Scope.** On a manager's page, **Scope** has a pattern on each line for the new conversations it starts out over in Add a Contact. A branch pattern takes the whole branch, in any letter case, where `*` is anything: `safa/release/*` takes `safa/release/v0.4.0`. A ticket key, in capitals with a dash, such as `COM-6*` or `COM-631`, takes a branch or an issue's or pull request's title that names that ticket: `com-631-bulk-tags`, or _COM-631: bulk tags_. Where several managers' scopes take one, the first in the list does. A scope only picks where Under starts: nothing already under a manager moves, and you can always pick another. Its **Team** and **Brief** tabs, its `@` tags and its tools cover the conversations under it alone. It is told the names of the project's other managers, and to leave their conversations to them.
- **Turning one off.** Use its own window's **Team > Turn off manager**, or its switch on its page. The project's menu says **Managers...** while two or more are at work. It turns off that manager alone: the others go on, and its conversations wait for it.
- **Deleting one.** Its conversations are under no manager. Delete the project's first, and the next one added takes its place, with what it was set up with.
- A project has up to eight managers, each with a name of its own, and a [project manager](#project-manager) over them.

**Its model.** **Model**, on the Manager page, is the selected service's model: **Default** uses that service's settings. As it takes a turn after every change, a smaller model uses less of your plan, which is why **Add a manager...** starts out with Sonnet. Pick one before you turn it on, or any time after, and its conversation switches at once. The model badge in its conversation changes it too, and the Manager page shows that.

**Switching services, including after a usage limit.** Click the model badge under the manager's message box: its menu lists the services that can run a manager (Claude, Codex, Gemini, OpenCode and Hermes), with a tick on the one it uses, above **Model...** and **Effort**. Pick another, choose **When it wants to do something**, and press **Switch service**. The manager answers with it from the next message. Pointed at, the badge says the service too. **Conversation → Service** lists the same, and so does ⌘K. Or open **Settings → your project → Manager**, choose the manager, select another **Service** and press **Switch service**. Both make the same change. A usage-limit message in a manager's conversation also offers **Switch manager service...** to open that page. The current turn stops and a fresh session takes over using the saved brief, recent conversation and waiting worker notes. The complete visible transcript stays in the same conversation, including an unfinished reply, across reloads, restarts and switching back. Manager history is kept without the ordinary contact’s 600-entry cap; switching does not copy old bubbles into a new transcript. Conversations archived by an earlier version remain in message history. Its identity, sources, scope, checks, instructions and assigned conversations stay. The model resets to the new service's default (Sonnet for Claude), and provider-specific effort and fast-mode settings reset too. Both switch flows offer only the destination service’s permission modes, starting with a conservative choice no broader than the current mode. If no such mode exists, you must pick one. A mode you explicitly pick is saved on the manager contact; the manager stays read-only in every approval mode. Cancel leaves its service, mode and running conversation intact. You can switch back the same way. This is a manual switch; each service needs its own CLI, login and external tools. A manager that is off stays off.

**Its workers.** A conversation a manager starts for a task answers with what **New workers use** says, on the manager's page in Settings. It doesn't simply take the manager's model and mode: a model picked for overseeing, and a mode that may never ask, are seldom what the work wants. **Permission mode**, next to it, sets the mode they start in: the service’s default, which is the mode Settings > [New contacts](settings.md#agents) picks for their service or else the service’s own, unless you choose **Same as the manager** (never looser) or pick a mode of their service.

- **Your defaults for new contacts**, which every manager starts with: the service, model and effort level of the contact you added last yourself, as Add a Contact starts out. A manager, and a conversation an agent started, are left out of that. With none, it is Claude with its default model. Settings > [New contacts](settings.md#agents) can pick the model and effort level instead.
- **Same as the manager**: the service, model, effort level and mode of the agent that starts it, as for any [started conversation](started-conversations.md). That is the manager, or a guest answering in its conversation, in the mode it has there: guests work read-only there, so their workers do too. A guest's worker is never in a looser mode than the manager's own: a manager in a read-only mode starts read-only workers. Where the guest's service has no mode that strict, the worker is the manager's own.
- **A service and model you pick**: pick its **Service**, **Model** and, where the model has levels, **Effort**, with the same pickers as Add a Contact.

A conversation a worker starts is like that worker, as any conversation's is. The manager's tool for starting one says that the worker is as these settings say.

**Automatic fallback.** A manager without guests can also follow the ordered rules in **Settings > Fallbacks**, or its project’s **Fallbacks** page, after a confirmed limit or repeated server failure. It keeps its brief, sources, assigned conversations and waiting notes. Each target’s spending rule still applies: switching automatically does not authorize charges. Managers with guests switch manually. See [fallback conditions and spending rules](accounts.md#continuing-with-another-provider).

**Sources.** On the same page, **Add source** for each place it learns what the project is building: a Linear project or tickets, a PRD in Google Docs or Notion, a Slack channel or thread, a Figma file, a doc in the repository. Give each a name, such as "PRD", and its link. One without a link works too, such as "#proj-tags on Slack". The manager reads them with the tools its service has, so connect Linear, Slack and the rest to each service you use. It also follows the links it finds in them, such as the thread a ticket links to.

**Or share a link with it.** Say it in the manager's conversation: _"here's the PRD: https://…"_. The manager adds the link to the sources, named by what it is, and reads it into the brief. The Manager page shows it at once. Ask it to drop a source that no longer holds, and it takes that one out.

**The brief.** What the manager learns goes into the project's brief: the goals, the decisions and where they were made, the acceptance criteria of each ticket, the open questions, and which conversation is on what. It writes the brief itself and keeps it up to date. The brief is on the Manager page, and in the **Brief** tab beside its conversation, for you to read. Edit it to set something right, and the manager is told what you changed. The brief is kept with the project, so it lasts when the manager starts a new chat or the app restarts.

**When its context fills.** The manager takes a turn after every change, so its conversation keeps growing. Once its context window is 70% full, well before Claude compacts it and loses what was decided, it is asked to bring the brief up to date with all a fresh session needs: where each conversation stands, the messages it sent that wait for an answer, and what it meant to look at next. Its window shows _"Its context window is 70% full, so it writes the brief for a fresh session to take over from."_ Once that turn is over, the conversation moves to the manager's message history, and a fresh session of the same manager takes over from the brief. It reads what the conversations it oversees passed on meanwhile, and their answers to its messages come to it. A message of yours still waiting is answered before it hands over.

**When it looks.** The manager hears from a conversation each time a round of its turns is over and an agent there wrote or edited a file. A turn you stopped, or one that went wrong, doesn't count. The manager's window shows a line, such as _"Claude (com-630-tags) changed 4 files: Tags are in…"_. Its agent is sent:

- the conversation's branch and folder
- what it was first asked, and its last reply
- the files it changed against the main line, with how many lines
- with the overlap check on, the files another conversation on the project changed too, whichever manager it is under
- what a reviewer the manager invited there said after the conversation's last reply (see **Reviewers in its workers** below)

The manager then finds the conversation's ticket, often named in its branch, and looks at the changes. It reads the files in that worktree, and asks the app for the diff.

It hears of a round once: one that says and changes just what the last one it heard of did is not passed on again. A conversation the manager [started](started-conversations.md) also tells it how a turn of its own ended, as any started conversation does, even one that changed nothing, such as a release's last report. Where that turn changed files too, the one note says both. A turn you start in that conversation's window, by writing to it there, is no news for the manager unless it changes files: you saw the answer.

After the first turn, ordinary progress replies wait while the worker has commands or watchers running in the background. A later reply replaces the held one; if the work ends without another turn, the latest held reply is sent then. Questions, approvals, failed or stopped turns and changed-file notes still get through without that wait. A card of questions it waits on reaches the manager as soon as it is asked (see **Answering a worker's questions** below). A note that needs no action can be answered silently, leaving only the usual time and cost line.

**Checks.** Tick what it looks for on the Manager page. All four are on to begin with:

- **Follows the design**: built the way the project is, as its instructions, its CLAUDE.md and the code on the main line have it.
- **Does what its ticket asks**: every acceptance criterion, and what was decided since, with tests.
- **Changes no file another one changes**: two worktrees that change the same file are likely to conflict when they merge.
- **Doesn't repeat or contradict another**: two conversations building the same thing, or deciding it two ways, such as names, APIs or data shapes.

**Your own checks.** Under those, **Add check** adds one of yours, a sentence each: _"Uses the design system's components, not plain HTML elements"_, _"Every new table has a migration that can be rolled back"_. The manager checks every change against them too, after the four. The ✕ on a row takes it out. Up to 20, each up to 300 characters.

**Instructions** are what it is told on top, such as how strict to be.

**Messages.** Where something has to change, the manager writes that conversation a message, and asks you first. Its window shows _"tagsapp manager would like to send Claude (com-630-tags) a message."_, with the message to read, and you are told where you aren't looking. **Accept** sends it: that conversation's window shows _"tagsapp manager says: Tags are per publication, not per post…"_, and its agent reads it once it is done with what it is doing. **Decline** sends nothing, and the manager stops there until you write to it. That conversation's answer goes back to the manager, whatever it changed: the round in which its agent reads the message, not one it was already in the middle of. Where all is well, the manager says so in its own conversation and messages nobody.

**Urgent corrections.** A manager can set `urgent: true` on `message_conversation` for “stop”, “do not push or merge”, or a wrong direction that must be corrected before work continues. It defaults to `false`. Approval and the per-user-message limit still apply. A waiting manager note in the worker's window has **Send now**, **Edit** and **Cancel**: Send now selects that note; Edit takes it out unread and puts the manager's words in your message box, to change and send as your own message, and **Put back** returns it to the queue as it was; Cancel drops it without putting the manager's text in your message box. Edit or Cancel, the manager is told that you took its message to edit, or cancelled it, before the worker read it, quoting its start, so it doesn't count on the worker having read it or send it again. That rides with the next news it reads rather than starting it; a message put back before then is never mentioned. The same goes for a project manager's message waiting for a manager, and a manager's report waiting for its project manager. An idle worker receives it as usual.

Urgent uses the same path as your **Send now**. Currently Claude calls the SDK's `interrupt()` and Codex sends `turn/interrupt`; both stop the active turn and start the selected message next, rather than injecting text into that turn. Codex resumes the saved thread in a fresh app-server after interruption and does not replay the interrupted command. An in-flight tool, including `git commit` or `git push`, may be interrupted by its provider. A command that already completed stays completed, and a remote push may have succeeded before interruption arrives. This is a correction request, not a guarantee that a command was prevented. The tool result reports “at its next step” when interruption was requested, or “waits until the worker is free” when delivery remains queued; it never claims the worker read or obeyed it. Other providers retain their existing Send now behaviour.

In a group conversation, the first active agent in its reply order reads the message, leaving paused agents alone, even if the manager mentions them. Agents set to answer after changes wait unless nobody else is active. If everyone is paused, the message waits until you resume an agent or ask one with @, and the tray says so. A nudge stops the group’s round: manager messages wait until you send another message, and the tray over the message box says _Held since you stopped: they go with your next message, or Send now._ Your next message reads them all with it, in the order they came. **Send now** on one gives that note a round of its own with the first active agent, as a message of yours would, hand-offs and the reviewer’s follow-up included; the others stay held, and no turn of that round reads them. An urgent message waits like any other, and the manager is told the user stopped the worker. **Send now** says why it can’t send only when no agent can take the note: everyone there is paused.

It asks as any contact asks before acting. Set its mode to **Never ask**, in its conversation window, and it sends its messages without asking. It stays read-only all the same: it still changes no files, and its mode badge says so when you point at it. A Codex manager keeps **Never ask** in its read-only sandbox, so the commands it may run, reading the web and starting workers don't ask either. In no mode can its commands, or an approval, give a manager or an agent in its conversation write access. buddylist declines a Codex request to run a command outside its read-only sandbox, without asking you, and tells the agent to start a worker for the change (see [Codex](codex.md)). A Claude manager or guest runs its commands in Claude Code's sandbox, which can't write in the project or the workers' folders, in every mode, **Bypass permissions** included. Reads and the network still work there without a prompt, such as `gh pr checks`, `gh api` or `curl`. `git fetch` writes into `.git`, so it fails, as it does for Codex. Where Claude Code's sandbox can't run, such as Linux without bubblewrap, a command Claude Code asks about is declined instead, and a session that starts in **Accept edits** or **Bypass permissions** doesn't start there, as nothing would keep its commands from writing. The conversation says so, and what to do: install bubblewrap, or pick a mode that asks first. It keeps its conversation, and picks it up once it can start. Gemini and OpenCode decline the commands they ask about.

A conversation is sent as many messages as **Hand-offs** in **Settings > Roles & teams** allows, six to begin with, until you write to it again. Past that, the manager tells you instead.

**Answering a worker's questions.** When a worker asks you something on a card of questions, such as Claude's "2 questions for you" with options to pick, and waits on it, its manager hears at once: its window shows _"Claude (com-850-reactions) asks 2 questions: How should keyboard users reach the reaction picker? …"_, and its agent is sent each question, its options with what each means, and whether it takes one option or any number. Where the brief, the sources or what you decided earlier settle it, the manager answers with its **answer_question** tool: an option by its label for each question, several where a question takes any number, or words of its own. Otherwise it leaves the card to you, and tells you what it asks.

- **Asked first, as a message is.** Its window shows _"tagsapp manager would like to answer Claude (com-850-reactions)’s 2 questions."_, with each question and its answer under it. **Accept** sends them. Under **Never ask** it answers without asking, as it sends its messages.
- **The worker goes on with them** as if you had answered. Its card shows each answer under its question and says _"Answered by tagsapp manager."_, and the line it leaves in the conversation names the manager too: _"tagsapp manager answered Claude’s 2 questions"_, with each answer, and on the phone _"tagsapp manager answered Claude’s question."_
- **The first answer counts.** Answer the card yourself first and yours stands: the manager is told what you answered, or that you skipped it. Once the manager has answered, the card is answered.
- **Questions only.** It never answers a permission, an approval to run a command or use a tool, a plan, project instructions to save, or an offer to go on in another account: those stay yours, whatever its mode.
- **Only its own workers.** It answers cards in conversations it oversees, one answer for each question on the card. An option the card doesn't have, too many options for a question that takes one, or a card that asks more questions than it answered is refused, and the card still waits.

**The Team tab.** Beside the manager's conversation, the **Team** tab lists the conversations it oversees in sections, each with a count: **Needs you**, **Working**, **Idle** and **Offline** (a conversation whose folder is gone). A worker it [drafted](started-conversations.md#starting-a-draft-or-deleting-it) for you to start is under **Needs you**, after the ones waiting on an answer: its buddy wears a play mark, and it says _Waiting to start_ under its name, with nothing at its end. Its head sums it up, such as "6 on shop · 2 working". Each row wears the same buddy as in the contact list, and says when it was last at work, or **Needs you**. Under its name, one at work says what it is doing. One whose turn is over while what it left [in the background](background.md) still runs is at work too: it is under **Working**, its buddy wears the arrow going round, and it says what runs over its branch and pull request. The others say their branch and, with a pull request, its size and the contact list's tags for it, such as **Conflict** or **2 failing**. The one that needs you stands out, and idle rows are quieter. Point at a row for its folder, its whole branch and its pull request. One with replies you haven't read shows how many. Click one, or press Enter on it, to show its conversation in that window. The tab opens with the manager's window, in front of its files. Its + brings it back once closed.

**The Brief tab.** **Brief** shows what the manager knows of the project, as it keeps it in its brief. It is drawn again whenever the manager saves the brief, or you change it. **Edit in Settings...** under it opens the brief on the Manager page, to change it there.

**Team row actions.** Right-click a conversation in Team, or focus its row and press **Shift+F10** or the **Menu** key, for **Open conversation** and **Add to message**. Add to message inserts that conversation’s existing @mention at the caret in your draft and returns focus to the message box. It sends nothing and works for conversations in separate worktrees too. **Invite to conversation**, below the separator, is a separate action: it uses the toolbar’s invitation rules to add an eligible contact as a guest. The menu explains when an invitation is unavailable, and prevents duplicate guests. Arrow keys choose an action, Enter runs it, and Escape returns to the row.

**Its window.** A manager changes no files and runs nothing, so its toolbar has **Contacts**, **Invite** and **Side pane**: no **Open in**, **Run** or pull request button. **Team**, **Brief** and its files are tabs of the side pane, which the side pane's **+** lists first, as the **View** menu does. The **Team** menu takes the place of **Code**, with **Team**, **Brief**, **Manager settings...**, **Project instructions...** and **Turn off manager**. In the contact list's palette (**⌘K**), the manager's conversation offers only **Invite**. A manager is one conversation, so its window has no [chat tabs](conversations.md#chat-tabs) to open: no **+** after its tab, no **Conversation → New chat tab**, and ⇧⌘A does nothing there. To use another service, switch the manager's service from its badge. For a side chat, add a new contact, which gets a worktree of its own. Chat tabs a manager had from an earlier version are ordinary contacts in its project now, not listed under it.

**Tagging a conversation.** In the manager's message box, type `@` and a list of the conversations it oversees opens: the ones the Team tab lists. Pick one with the arrow keys and **Enter** or **Tab**, or with the mouse, and its tag goes in, such as `@Claude (com-630-tags)`. A tag points: _"what's left for @Claude (com-630-tags)?"_ tells the manager which conversation you mean. It sends that conversation nothing. The message goes to the manager alone, which still messages a conversation only with its own tool, after asking you. The manager writes the conversations it names as tags too. A tag, in your message or in its reply, is marked: click it to show that conversation in the window, as a row of the Team tab does.

**Talking to it.** The manager is a contact like any other: ask it "how is everyone doing?", "what's left on COM-630?", or "catch up on Slack". It can list the conversations under it, with what each is doing and what it changed. Ask it to "start a worker for the bulk tags ticket, with Codex to review", and it [starts a conversation](started-conversations.md) for it, in a worktree of its own, with Codex in it from the start.

**Reviewers in its workers.** Ask it to _"invite a Claude Opus reviewer into each worker"_, and it invites one into each worker's own conversation with its **invite_to_conversation** tool, instead of running subagents of its own. The reviewer is a guest there, as one you add with **Invite**: the worker's window says _"tagsapp manager invited Claude (Opus 5.5) as Reviewer."_, and its **Agents** tab lists it with its model, **after changes**, **read only** and **invited by tagsapp manager**. The manager can pick the service, a model by its id or its name (_claude-opus-5-5_ or _Opus 5.5_), an effort level its model takes, and a role from **Settings > Roles & teams** by name; a model or level the service doesn't have is refused with the ones it has.

- **A reviewer unless a role says otherwise.** Without a role it changes no files, answers once the worker has changed files, and hands what has to change back to the worker with `@`. Codex reviews in **Read only**, Gemini and OpenCode in **Plan**, and Claude without the tools that write files. Hermes can't work read-only, so it can't review. With a role, it does what the role says, with its rules, when it answers and whether it changes files.
- **What it is to look at.** With a message, such as _"review against COM-630's acceptance criteria"_, it starts on it once it has the turn: at once in a worker that is idle, after the worker's turn in one at work. It is also told the message from then on. Without one it waits for the worker's next change.
- **Hand-offs stay limited.** Reviewer and worker take turns as any agents in one conversation do, and stop at **Hand-offs** in **Settings > Roles & teams** until you write.
- **What it found reaches the manager.** Once the round is over, the manager's window shows a line such as _"Reviewer reviewed Claude (com-630-tags): One bug in app/tag.rb:4…"_, and its note has the worker's own last reply and what the reviewer said after it.
- **Asked first, unless you asked.** An invite you asked for goes ahead. One the manager thought of asks you first, on a card that says who joins which conversation, as what, and what it is to do. A manager acting on a project manager's message you didn't approve asks too.
- **Only its own workers.** It invites into conversations it oversees, not ones put away, nor its own conversation, nor another manager's. One already there is not invited twice, and a conversation holds up to 10 agents besides its own.

When you ask it to fix something or approve work it proposes, it starts the worker with buddylist’s conversation tool. You do not need to ask for a new contact by name. The worker gets its own worktree and follows **New workers use**. The manager stays read-only; internal subagents of its service inherit that restriction rather than becoming coding contacts. Any protected app action that needs approval is shown in the conversation.

The manager is told to start workers once it can give them concrete tasks, before broad tool discovery or investigating every fix itself, and to confirm which workers actually started. A Codex conversation with no progress update for a minute shows a notice, with its last reported activity when available. This also covers tool calls Codex does not report as activity. It does not interrupt or retry the call; **Stop** and **Send now** remain available. Time spent waiting for your approval does not trigger the notice.

Good to know:

- **It takes a turn after every change**, on your Claude plan. Turn it off when you don't need it, with **Turn off manager** in the project's menu or on the Manager page: the contact stays, with its conversation, and oversees nothing until you turn it on again. **Add a manager...** then brings the same one back.
- It oversees the conversations under it, whatever their service: Codex and Gemini contacts too. Archived ones are left out, and are under it again once restored.
- Each line in a conversation's window says who it is from, and so does what its agent is sent: a manager's message is never taken for yours.
- Delete the manager's contact and the conversations under it are under no manager. Adding one again adds a new one, which starts with none of them. One you renamed keeps its name when it is turned off and on.
- A worker started with the app's tools answers with what the manager's **New workers use** says (see **Its workers** above). With **Same as the manager**, it uses the service, model, effort and permission mode of the agent that starts it: when Codex is answering in a paused Claude manager's conversation, it starts Codex workers under that same manager. To change the manager itself to Codex, use **Conversation → Service → Codex** or **Switch service** in its settings.
- A folder outside a git repository has no worktrees to oversee, and its Manager page says so.
- **Guests work read-only, as part of the manager.** An agent you invite into a manager's conversation is a reviewer, a second opinion or a stand-in for the manager, as the manager changes no files: it joins in its service's mode that changes none. Codex is in **Read only**, Gemini and OpenCode in **Plan**, and Claude asks before acting, goes without the tools that write files, and runs its commands in Claude Code's sandbox, which writes nothing there. Its mode stays that way: in the Agents tab, its mode's menu shows it greyed out, with why. Hermes has no such mode, so Invite greys it out on every tab: _Hermes can't join a manager read-only_. Work goes to a worker, in a worktree of its own: ask the manager to start one, or add a contact under it with the + on its row. A guest that joined before this version works read-only from its next turn, and the conversation says so once, such as _Codex now works read-only here_. A Hermes guest from then sits out, paused, and doesn't answer there even when you mention it: the conversation says why. A guest stays read-only when its service changes, in the new service's mode for that, and one that switches to Hermes sits out the same way.
- **A guest answers as part of the manager.** It is told it is in the manager's conversation, changes no files there, and has the manager's tools (starting workers, messaging them, the brief and the sources). Pause the manager and ask a guest for a change, and it starts a worker with buddylist's conversation tool, listed under the manager and following **New workers use**, instead of editing the main checkout. One without a role is told everything the manager is told, so it also reads the workers' notes and keeps the brief while the manager is paused. One you invited with a role, such as a reviewer, does its role's job and hands what has to change to a worker, leaving the brief and sources to the manager. A guest in a project manager's conversation hands work to the managers with message_manager, as the project manager does. The agents take turns on each message, and each is told not to start what another already started. Invite still adds a guest beside the manager, and **Switch service** still changes the manager itself.
- A manager with guests is a group too: there, `@` and an agent in the conversation is a mention, which says who answers, and the conversations it oversees are tags, listed after the agents. A conversation that is in it as a guest is mentioned, not tagged.
- In demo mode, a manager asked after a conversation it tags, or after everyone, looks and answers with tags. A manager that is turned on writes a made-up brief, and a link you send it is added to the sources, named after its site. A conversation that then changes files, say after "fix", is asked for the test its ticket wants, once you accept the message, and answers that it is on it.

## Project manager

A project with managers can have a **project manager**: a manager over its managers, which hands work from one team to another as you tell it. It has no rules of its own for that: you say what to do, such as _"send the coder manager's finished jobs to the review manager"_, and it does just that.

**Adding one.** Right-click the project and choose **Add a project manager...**, or press it on the project's **Manager** page in Settings. It is offered once the project has a manager. The dialog asks for its **Name**, **Service**, **Model**, Claude with Sonnet to begin with, and a **First source**. A project has one: it oversees all of the project's managers at work, and none of its conversations. Its right-click menu, and the project's, then has **Project manager settings...** and **Turn off project manager**.

**In the contact list.** It leads its project's section, with its managers under it, each set in a level, and their conversations under them. Its row says how many managers it oversees, and its count folds them all away; each manager under it folds its own conversations, as before. Nothing is put under it: Assign to manager, Under in Add a Contact and dragging offer only the managers. A manager turned off, or put away, is no longer under it, and a project manager turned off leads nothing until it is on again.

**The chain of command.** You talk to the project manager; it talks to the managers; they talk to their workers.

- **Handing a job on.** Its **message_manager** tool sends one of its managers a message, and with **job** set to a worker of the project, that worker's job: its branch, folder, pull request, task, last reply and changed files. That manager starts its own workers for it, such as a reviewer, with its own **New workers use** and permission mode.
- **Its answer.** The round in which a manager reads the message goes back to the project manager, as a worker's answer goes back to its manager: its window shows _"review manager answered: …"_. A result that comes later, such as a review's verdict, the manager sends up with its **message_project_manager** tool: _"review manager reports: …"_.
- **Passing a verdict back.** The project manager sends it to the manager of the worker it is about, with **job** set to that worker, and that manager tells its worker with **message_conversation**, which asks you, as it always does.
- It never messages a worker, and starts no conversation: the managers do, so they always know what was said to their workers.

**Approval.** Each message it sends asks you first, on a card that says whom it is for and whose job it hands on. A message you approved is work you asked for: the conversations the manager starts for it start at once. One that went without your approval, as the project manager's mode never asks, is that manager's own idea: what it starts for it is drafted, and waits in its message box for you to send, until you write to that manager yourself. A draft says it waits to start in the list, in Team and in the conversation that drafted it, with **Start** (see [Started conversations](started-conversations.md#starting-a-draft-or-deleting-it)). A manager is sent as many of its messages as **Hand-offs** in **Settings > Roles & teams** allows for each of yours to it, and a manager sends it as many reports for each of yours to the project manager.

**When a manager can't answer.** If the round that read its message was stopped or went wrong, the project manager is told so, and that the message waits until you write to that manager. If a manager it handed a job to is turned off, put away or deleted before it reported on it, the project manager is told which jobs nobody is on now. A message to a manager that is off, put away or no manager of the project says which managers are at work; one to a manager you stopped waits, also an urgent one.

**What it knows.** It hears from its managers alone: their answers and reports, each a short outcome. It is never sent their workers' changed-file notes. Its **project_teams** tool looks when it needs to: without arguments, each manager and the 20 workers most recently at work, a line each, with how many more there are; with a manager, that team, with each worker's task and changed files; with a conversation, that worker's job. It reads no diffs: the reviewers do. Like a manager, it keeps a **brief** and **sources**, has **Instructions**, and hands over to a fresh session when its context window is 70% full. Its Settings page has no checks, scope or New workers use: it has no conversations of its own.

**Read-only.** It is a manager: it changes no files, its guests work read-only, and it has the **Team** and **Brief** tabs. Its Team tab lists its managers, each with how many conversations it oversees, and `@` in its message box tags its managers and the project's conversations.
