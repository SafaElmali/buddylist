# Adding a provider

[`src/providers/codex/`](../src/providers/codex) is a good example to copy: it drives a CLI over stdio, with no SDK.

A CLI that speaks the [Agent Client Protocol](https://agentclientprotocol.com) needs much less. [`src/providers/gemini/`](../src/providers/gemini) is a descriptor and a few lines on top of the shared [`acp/`](../src/providers/acp) session; start there and skip step 2.

1. Create `src/providers/<id>/` with an `index.js` that exports a [`Provider`](../src/providers/contract.js): a `descriptor` and a `createSession({ contact, emit })`.
2. Implement the session by extending [`BaseSession`](../src/providers/base-session.js):
   - Turn the agent's output into the session events.
   - Map its tool calls to activities.
   - Ask for approvals with `this.requestPermission(...)`, which returns the user's decision.
   - If the agent has helpers (subagents) and says what they do, tell which step is whose and when each helper ends, as [`contract.js`](../src/providers/contract.js) describes under its session events. Add `stopHelper`, and `helpers: true` to the descriptor. [`claude/session.js`](../src/providers/claude/session.js) does all of it.
   - If the agent leaves commands running in the background and says when each starts and ends, emit `background` with all of them whenever that changes, and add `stopBackground` and `backgroundOutput`, with `background: true` in the descriptor. The window then has a **Background** tab. [`claude/session.js`](../src/providers/claude/session.js) does it with [`claude/background.js`](../src/providers/claude/background.js).
   - If the agent can go back to just before a message the user sent, and forget it and everything after, add `rewind(id)`, with `rewind: true` in the descriptor. Each message it can go back to is sent with an `id`. The conversation window then lets the user edit what they sent. [`claude/session.js`](../src/providers/claude/session.js) does it with Claude Code's `resumeSessionAt`.
   - If the agent can copy its conversation up to one of its replies, for another session to go on with, add `fork({ text, later })`, with `fork: true` in the descriptor. The conversation window then offers **Fork chat from here** under a reply. [`claude/session.js`](../src/providers/claude/session.js) does it with the SDK's `forkSession`.
   - If the agent can say how full its context window is, emit `context` after each turn and add `usage()`, with `usage: true` in the descriptor. The conversation window then has a meter for it, and answers `/context` and `/usage` itself.
   - If the agent reads settings that run commands from the folder it works in (hooks, MCP servers, plugins), and can be told to read them from another, pass `createSession`'s `mainFolder` on to it, as [`claude/session.js`](../src/providers/claude/session.js) does. A contact's worktree can be anyone's pull request; `mainFolder` is the same folder in the project's main checkout. If it can only be told not to read them, do that, and hand it what it then skips, such as `AGENTS.md`, as [`codex/worktree.js`](../src/providers/codex/worktree.js) and [`opencode/worktree.js`](../src/providers/opencode/worktree.js) do.
3. Register it in [`src/providers/index.js`](../src/providers/index.js). The **Add a Contact** dialog then offers a **Service** choice.
   - If the agent can list its models without starting a conversation, give the provider a `listModels()`, as [`codex/models.js`](../src/providers/codex/models.js) does. The dialog then offers that list in place of the descriptor's `modelSuggestions`.
   - If the agent has a quick model it can be asked one thing of, give the provider a `nameTask(message)`, as [`claude/task-name.js`](../src/providers/claude/task-name.js) does: a few words for the task a message asks for. A new contact's branch, and the nickname made up from it, are then named after the first thing it is asked in those words. Without one, the words of the message itself stand in.
   - With such a model it can also have a `suggestReplies(reply, { asks, model })`, as [`claude/suggest-replies.js`](../src/providers/claude/suggest-replies.js) does: what the user might send after a reply, as they would type it. To a reply that `asks` them something, a few replies, which the conversation offers under it to send with a click; to any other, the one message they would most likely send next. The first is offered grey in the empty message box, for Tab to write in. Without one, nothing is offered. `model` is the conversation's: pick the quick model from what the account lists, as [`codex/quick-model.js`](../src/providers/codex/quick-model.js) does, and ask that one when it lists none, since a model the account doesn't have fails.
   - Give the provider a `checkSetup()`, as [`codex/index.js`](../src/providers/codex/index.js) does with `cliSetup` from [`setup.js`](../src/providers/setup.js): the command that leaves with 0 only when the CLI is signed in, and what to tell the user when it is not installed or not signed in. The [welcome wizard](welcome-wizard.md) then lists the service with how it stands. Without one it says the service could not be checked.
   - A CLI that signs in through the browser by itself, with no terminal to type in, can be signed in from the wizard: list the ways in the descriptor's `signIn`, and give the provider a `signIn({ way, signal })` that runs the CLI's sign-in with `cliSignIn` from the same file, as [`claude/index.js`](../src/providers/claude/index.js) does. Its line then has a **Sign in...** button while it is not signed in.
   - If the agent keeps the conversations held outside the app where they can be read, in a terminal say, give the provider an `elsewhere`, as [`claude/sessions.js`](../src/providers/claude/sessions.js) does: a `name`, a `list(cwd)` and a `read(cwd, id)`. A contact's message history then lists them among its own, to read and search. Leave out the ones the app itself started.
   - A CLI that keeps its login in a folder it can be pointed at can be signed in to more than one account, as [`claude/accounts.js`](../src/providers/claude/accounts.js) does with `CLAUDE_CONFIG_DIR`: say `accounts: true` in the descriptor, and give the provider an `accounts` with `status`, `signIn`, `signOut` and `prepare` for a folder, and `limits` if it can say what a login has used of its plan, which the status bars show as soon as that login is put in use. The app keeps the list ([`main/accounts.js`](../src/main/accounts.js)) and hands the provider an `AccountSwitch`: its sessions start in the one in use, and one whose account reaches a limit can offer to go on in the next. A session with `accountSwitched` is told when another is put in use, to say what happens to a turn in progress. See [Accounts](accounts.md).
4. Draw its display picture in [`src/renderer/lib/pictures.js`](../src/renderer/lib/pictures.js), under the avatar id from the descriptor.
5. Add tests next to `test/codex-session.test.js`. That file drives a session with a fake app server and shows the pattern.

Nothing else in `src/main/` or `src/renderer/` should need to change.
