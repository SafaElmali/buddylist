# Landing page

```bash
npm run build:site
npx serve dist/site
```

This builds [`site/`](../site) into `dist/site/`: a static page with the browser preview embedded as a live demo.

The landing page uses [`index.html`](../site/index.html), [`site.css`](../site/site.css) and [`site.js`](../site/site.js), with small modules for download selection and visitor counts. The footer links to Product Hunt. There is no frontend framework. The build fills [`changelog.html`](../site/changelog.html) from [`changelog.md`](../site/changelog.md), includes [`sponsor.html`](../site/sponsor.html), and fills [`docs.html`](../site/docs.html) once for each guide.

- **The hero is the app as a developer sees it first** (`.hero`): what it does on the left, and on the right a conversation and the contact list in the professional look, the look a new install starts in. They are screenshots of the app in demo mode, `hero-professional-*.webp` and `hero-messenger-*.webp`, a group chat with its diff in the **Changes** tab and a project's contact list. The **Professional** and **Messenger 2005** switch over them shows the other pair and puts the 2005 sky, Luna's buttons and its type behind the hero, and the line under them changes with it. Without scripts there is no switch, and the professional look stays. Four lines under it (`.points`) say what sets buddylist apart. The **New** pill links to the changelog, highlighting v0.7.2: the source opened under the MIT license, and Claude stopping at the plan limit instead of using usage credits. The conversation card's invitations line links to the [remote access guide](remote-access.md) for answering them from a phone, and the browser card says a picture an agent shared can be drawn on too. Its unversioned link keeps working while the next release builds; the changelog only lists published versions.
- **The page is in the professional look**, as the app is from its first start: the system's type, slate by day and ink for the header, the night band, the way out and the footer. Every window on it is drawn as the app draws it there (`.look-pro`, by day with `.day`): the toolbar on the title's row, a name over each reply, your own messages in bubbles. The page's own windows (the comparison of ways, the downloads and feedback) are `.sheet`s, drawn as the app draws a dialog. The 2005 messenger is kept for where the page shows it off: the hero's switch and **Two looks**, which set its type and Luna's colours with `.xp-type`.
- **The artwork is the app's own.** A token such as `__TB_RUN__` or `__EMO_SMILE__` in `index.html` is replaced by that drawing from [`icons.js`](../src/renderer/lib/icons.js) or the emoticons: `TB_` is the toolbar's set, `SM_` the small icons, `LI_` the contact list's, `TAG_` the pull request tags, `NEXT_` the buttons after a merged one and `WIN_` the window buttons. `__PRO_ICONS__` writes the professional look's line icons, from [`pro.css`](../src/renderer/styles/pro.css), for a window drawn in that look, and for the page's own cards beside them (`.pro-icons`). [`scripts/site-artwork.js`](../scripts/site-artwork.js) has them all, and [`scripts/build-site.js`](../scripts/build-site.js) stops on a token it doesn't know.
- **The small windows play a scene each**: the contact list, a conversation, a group conversation and the pane beside one. The manager's window stands still. They are plain markup styled like the app, and `site.js` plays them while they are on screen. A line of a conversation says in its attributes how it arrives: `data-type` is typed into the message box first, `data-typing` names who is writing while it is waited for, and `data-wait` is how long. In the conversation, `data-todo` on a line moves the agent's to-do list under the newest line on to the step it names once the line has arrived, or puts it away (`away`) when the agent stops. The line under the list says what the agent is doing on that step, from the step's `data-doing`, with a clock.
- **Group chats have a band of their own** (`#group`). In its window, a mention (`<span class="at">`) in a typed line opens the list of names over the message box, as `@` does in the app, and `data-by` on a line says whose turn it is: that agent's buddy is Busy and its row in the Agents tab, on the right as in the app's side pane, lights up.
- **Project managers have a band of their own** (`#manager`), the manager's window as the app draws it, with **Team** in the menu bar where **Code** is, no **Open in** or **Run**, a message it asks to send, and the **Team** tab beside the conversation, by who needs you, who is working and who is idle. Its copy explains starting from another manager’s settings and brief, choosing worker defaults, service choice and keeping the brief and team when switching, and the project manager over the managers, which hands a job between teams and asks before each hand-off. Team rows can open a conversation or add a mention to a draft. It links to the account allowance dashboard and optional switching before a limit, states that this is not a spending cap, and keeps the fallback Never spending rule’s limitation.
- **The pane beside the conversation has two halves**, as in the app: the tabs above (a plan, Changes, a web page, Subagents, Session) and the terminal below. Each card next to it shows its tab, and they take turns until someone picks one.
- **The phone app has a band of its own** (`#phone`), the last of the features: four cards (who needs you first, private on your own tailnet, notifications, a level for each phone) and beside them two phones, a plan on an Android phone at night (`phone-plan-dark`) and Home on an iPhone by day (`phone-home-light`). They are screenshots of the real phone app, paired with the app in demo mode through a fake Tailscale, at each phone's Home Screen size. Each is an AVIF with a WebP for browsers without it, at twice the size it is drawn, with its width and height set so nothing moves as it loads, and loaded only as it nears the screen. The line under them says where it works and links to the [remote access guide](remote-access.md).
- **The film and the live demo share one place.** Under the tour's heading, wide screens have **Watch the tour** and **Try it live**: the second puts the monitor in the film's place and pauses it. The demo loads the first time it is asked for, as `demo/index.html#tour`, which [plays a tour](browser-preview.md) until someone clicks in it. The demo tells the page when the tour plays and when it is over, which changes the line under the monitor, and **Replay the tour** asks it to start again. **Professional**, which it opens in, and **Messenger** under it switch the demo's look, and follow it when the demo's own **Tools > Look** changes it. Phones, and a page without scripts, keep the film and the link under it to the full-screen demo.
- **The 30-second tour** (`#tour`) is the promo film under the hero, under the four lines. It plays muted once most of it is on screen, as browsers allow, and stops when it is scrolled away. **Sound on** starts it over with sound. Wide screens play `promo.mp4`, others the lighter `promo-720.mp4`, and `promo-poster.jpg` stands in until it plays. It is the launch film, and the three files are committed with the page.
- **Two looks** (`#looks`) is where the page shows off the messenger: the group chat's window in the professional look, with ☰ and the toolbar on the title's row, and on the right of a line that follows a drag or the arrow keys, a copy of it, made by `site.js`, as the 2005 messenger draws it. **Night** and **Day** are the professional look's. Its styles are `.look-pro`, at the end of `site.css`.
- **Short by design.** Each part of the page shows one window and says a few lines about it, and a link under it goes to the guide that says the rest. A card beside a window is a line or two, and the contact list and the conversation have three each: a new feature takes a card's place only if it is stronger, and otherwise goes in its guide. The contact list’s cards include scheduled prompts, with a link to their guide and the requirement to keep buddylist open. The terminal card explains sharing output with @ or a selection. The comparison (`#mapping`) has the eight rows that matter most to someone coming from a terminal: a line of the terminal on the left, and on the right what buddylist has instead, its name in bold. The questions are the eight a visitor asks first, in two columns; the rest are in [Questions and answers](faq.md), under topics.
- **Nothing moves for someone who asked for that.** With `prefers-reduced-motion`, the scenes show how they end, nothing slides, drifts or shakes, and the tour waits for a click. Without scripts the page is all there, standing still: the tour is a plain video with its own controls, and the comparison shows the professional look.

- `SITE_URL` sets the page's public address. It defaults to `https://buddylist.dev`.
- Set `ELECTRON_SKIP_BINARY_DOWNLOAD=1` on the host so installing doesn't fetch Electron.

## Search and link previews

The build also writes what search engines, AI assistants and link previews read. All of it is worked out from the words in [`site/index.html`](../site/index.html) by [`scripts/site-seo.js`](../scripts/site-seo.js), so there is nothing to keep in step by hand. A feature is any `<h3>` in the features section with a `<p>` right under it, in the band it is in: an `<h2>` with its `eyebrow` label over it and its `intro` under it, such as **Project managers**. A question is a `<details>`:

- structured data in the page's `<head>`: the site, the app and every question in the FAQ. The app is free only while a question asks whether it is and its answer starts with "Yes.", its download points to the section with every platform's installer, its other pages are the header's GitHub and X links and Product Hunt, and its version is `package.json`'s. It never claims a rating or reviews.
- structured data in each guide's `<head>`: the guide as an article, the trail back to the docs and the landing page, and the day it last changed
- `robots.txt` and `sitemap.xml`, which lists the landing page, the changelog, the sponsor page and every guide, each with the day its file was last committed (the deploy checks out the whole history for it)
- `llms.txt`, the page's features, under their bands, and questions as Markdown for language models, and `llms-full.txt`, the same with every guide in full after it

The questions link to the guide for what they answer, and a test checks every such link goes to a guide on the site.

[`site/_headers`](../site/_headers) asks Cloudflare to keep the demo's windows out of search results.

The picture shown when the page is shared is [`site/og-image.png`](../site/og-image.png), a photograph of [`site/og-image.html`](../site/og-image.html). Run `npm run og-image` to retake it after `npm run screenshot` or a change to the card. The same run writes the card at GitHub's 1280×640 to [`docs/social-preview.png`](social-preview.png), the repository's social preview: upload it by hand under **Settings → General → Social preview**. On X, every page's preview names [@buddylistapp](https://x.com/buddylistapp) as the site's account (`twitter:site`).

## Changelog

**https://buddylist.dev/changelog** lists every version and what is new in it, newest first, a card each with an anchor of its own (`/changelog#v0.2.9`). The app's **See changes**, **What's new** and **Help > What's new** open it, and the landing page links to it from the header, beside the download button, in the questions and in the footer, as it does to [the docs](#docs). Beside **Download**, the header has three icons: the [GitHub repository](https://github.com/SafaElmali/buddylist), buddylist on [X](https://x.com/buddylistapp) and **Buy me a coffee**. It shows its links from 1070px wide, where they fit on one line with the icons; narrower, it keeps the name, the icons and **Download**, and under 360px only the name and **Download**.

- **It is written by hand** in [`site/changelog.md`](../site/changelog.md): each version under a `## v1.2.3 — 2026-10-12` heading, newest first (the day can wait), and what is new in it in Markdown under that, for the people who use buddylist, a change a line: `- **What changed** — what it means for you.` A release takes its version's part as its description on GitHub (see [Releases and updates](releases.md#whats-new)).
- **The build writes the page.** [`scripts/site-changelog.js`](../scripts/site-changelog.js) reads the file with [`src/shared/release-notes.js`](../src/shared/release-notes.js) and writes the versions into [`site/changelog.html`](../site/changelog.html) where it says `__RELEASES__`, as `dist/site/changelog.html`. The page is a static file like `index.html`, and asks nothing of GitHub. A version with nothing under its heading links to its downloads.
- **It is made to scan.** Each version is a card whose line says which, when and how many changes. Only the newest is open; the others list the names of their changes until you open them. An open card shows each change's title and first sentence, with the rest under **More**, and **Smaller fixes** as a list, a fix a line. The build cuts a change into sentences without changing its words: never inside code, a link or bold, nor after a menu item's `...`, and a sentence that leans on the one before ("It…") stays with it. A change it can't cut is shown whole. Beside the cards, the versions are listed to jump to; on a phone they are a row to swipe through over them.
- **It reads without scripts.** Every card opens by its line. [`site/changelog.js`](../site/changelog.js) only opens the card a link points to, such as the app's **What's new**, and shows **Expand all** and **Collapse all**.
- **Only published stable releases are listed.** The deployment's download check exports `SITE_RELEASES` from GitHub Releases. A version prepared in `package.json`, a draft, or a tag without a published release stays off the page. Publication dispatches a site deployment; notes added after publication appear on the next site deployment. The same metadata supplies the landing page's structured-data version. Offline builds omit these release claims unless given a `SITE_RELEASES` fixture; see [Releases and updates](releases.md#credentials-and-permissions).
- **A mistake fails the build**: a `##` heading that isn't a version, a version twice, or a day that isn't one. The site's checks on a pull request catch it, and its tests check that the versions are newest first.

`npm run build:site` builds the page into `dist/site/changelog.html`.

## Docs

**https://buddylist.dev/docs/** is the guides in [`docs/`](.) for the people who use buddylist, a page each: every guide listed on the left as XP's task pane would, the guide in the middle, and on wide screens its headings on the right under **On this page**. Getting started is `/docs/` itself, and every other guide is `/docs/<its file's name>`, such as `/docs/run-button`. Each page is also served as the Markdown it is written in, at its file's name (`/docs/run-button.md`), and `llms.txt` lists the guides by those. The landing page and the changelog link to the docs from their header and footer, and the app's **Help > Help topics** opens them.

- **Which guides are on it** is the list in [`scripts/site-docs.js`](../scripts/site-docs.js), under the headings the left side has, each with the sentence a search result shows for it. The **Using it** guides in the [README](../README.md#guides) are that list, and a test checks the two agree: add a guide to both.
- **A guide is written for GitHub and the site alike.** A heading has the anchor GitHub gives it, so `settings.md#scripts` works on both, and a link to another guide becomes a link to its page.
- **A link the site can't follow fails the build**: one to a file that is not a guide on the site, such as `../README.md`, `browser-preview.md` or something in `src/`, or to a heading a guide doesn't have, and a picture from the repository. On the site it would go nowhere, or to the private repository. Link to a guide, to the [live demo](https://buddylist.dev/demo/) or to another full address instead.
- **The pages need no script.** On a phone the guide comes first, with the list of guides under it.
- [`site/_headers`](../site/_headers) keeps the Markdown out of search results, so a search finds the page.

`npm run build:site` builds them into `dist/site/docs/`.

## Sponsor

**https://buddylist.dev/sponsor** is the page for sponsors. The header and the footer of every page link to it, and so does the line under the feedback form. Like the changelog, it is a static page with no script of its own.

- **A letter**, signed by whoever makes buddylist, on why sponsoring matters.
- **Three ways to give**: [Buy me a coffee](https://buymeacoffee.com/safaelmali), [GitHub Sponsors](https://github.com/sponsors/SafaElmali), and **As a company**, which goes to the company part. The accounts are the ones in [`.github/FUNDING.yml`](../.github/FUNDING.yml), the **Sponsor** button on GitHub, and the page's tests fail when the two differ.
- **Sponsor as a company** (`#company`) says what a company's sponsorship brings, and starts it on GitHub Sponsors, as an organization, or with a message on [X](https://x.com/safaelmali) first.
- **Sponsors** (`#sponsors`) is a contact list. Each sponsor is a row in it, `<div class="row">`, with its logo where the buddy is, its name in `<b>` and what it does in `<span class="line">`; count it in the group's line. Until the first, the list says nobody has signed in yet. The link under it goes to GitHub Sponsors, not back up to `#company`: from the bottom of the page, that jump has nowhere to scroll.

## Downloads

The header, hero and closing download buttons use [`site/site-downloads.js`](../site/site-downloads.js) to choose the visitor's desktop OS: the Apple Silicon DMG on Mac, the x64 installer on Windows, or the x64 AppImage on Linux. The button label names the platform, and the download cards state each build's architecture and installation details. Browser OS detection cannot reliably identify every processor; a recognized ARM Windows/Linux browser gets the chooser instead.

**All downloads** shows three platform cards above the setup instructions: the Mac DMG, Windows installer and Linux AppImage, with a secondary Debian package link. The detected OS is highlighted with **This computer**; the cards stack on narrow screens. Phones, tablets, ChromeOS, unknown browsers and visitors without JavaScript go to this chooser with no platform highlighted. The changelog, docs and sponsor page also link there. All four installer links work without JavaScript or an email address, and point to the latest release in [the public repository of releases](https://github.com/SafaElmali/buddylist/releases). macOS releases are signed and notarized; the Windows installer is currently unsigned. Debian packages are updated through the package manager; installed Mac, Windows and AppImage copies offer Restart to update.

Follow [Releases and updates](releases.md) first. The deployment workflow runs [`scripts/site-downloads.js`](../scripts/site-downloads.js) and waits until every advertised installer is uploaded to the latest public release. When one is missing, it checks the build and keeps the current site live. Publishing a release starts site deployment again. Once live, the same installer links serve each new release without changing the page.

## Visitor counts

The page counts its visits and its downloads with PostHog, without cookies. The build writes PostHog's loader into the page where `index.html` says `__ANALYTICS__`, and writes nothing there while no project is filled in. See [Analytics](analytics.md) for what is counted and how to set it up.

## Deploy to Cloudflare

The landing page is hosted at **https://buddylist.dev** (also available at `www.buddylist.dev`) using [Cloudflare Workers static assets](https://developers.cloudflare.com/workers/static-assets/). Every request to `agent-messenger.tsafaelmali-b18.workers.dev` permanently redirects to the same path and query string on `buddylist.dev` with HTTP 308. The Worker runs before static assets so the redirect also covers the homepage, demo and files.

```bash
npx --yes wrangler@4 login   # once, if this machine isn't already signed in
npm run deploy:site
```

[`wrangler.jsonc`](../wrangler.jsonc) selects the Cloudflare account, the `agent-messenger` Worker and its `FEEDBACK` store. Each deployment runs `npm run build:site` and uploads `dist/site/`, including the browser demo, along with the Worker.

[`Deploy site`](../.github/workflows/deploy-site.yml) automatically builds the website when a push to `main` changes site inputs: the landing page, browser demo and its shared app code, copied artwork, the guides in `docs/`, build scripts, dependencies, site tests or deployment configuration. It deploys once the [download check](#downloads) passes. App-only backend changes do not trigger it. Pull requests use the same path filter to run the site tests and build the page and browser demo. You can also redeploy from **Actions → Deploy site → Run workflow**, selecting `main`; running it on another branch only checks the build. Deployments from `main` run one at a time.

Before the first automatic deployment, add a repository Actions secret named `CLOUDFLARE_API_TOKEN`. Create it using Cloudflare's **Edit Cloudflare Workers** token template, scoped to the account in `wrangler.jsonc`; see [Cloudflare's GitHub Actions authentication guide](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/#1-authentication). The account ID is already in `wrangler.jsonc`, so no account ID secret is needed. A local `wrangler login` does not authenticate GitHub Actions.

Optionally set the repository Actions variable `SITE_URL` to override the public address used in metadata. Without it, the build uses `https://buddylist.dev`. The manual deployment command remains available.
