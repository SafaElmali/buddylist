# PR stacks

Open **View PR stack...** from the PR button’s menu or Code menu, or choose **PR stack** from View or the side pane’s **+**. The view shows the current conversation’s verified pull request with the rest of its GitHub stack, or else its base/parent PRs and dependent PRs by branch, and says which of the two it shows. It reads top first, as GitHub's own stack popover does: a rail of nodes runs from the top PR down to the base branch, so that what a PR builds on is below it. Each row links to GitHub and shows the PR's number, title, state (an icon, a theme colour and a word for open, draft, merged or closed) and head branch. The current PR is highlighted and labelled. The header names the stack, counts its PRs and says how many are merged. Refresh asks GitHub for current metadata.

Pin the tab with its pin button or context menu to keep it available across window reopening and app restarts. Pins belong to this conversation. Archived conversations can still read the stack. A missing checkout retains an unavailable pinned tab; its context-menu **Close** or **Unpin** removes it.

## GitHub stacks

GitHub’s own stacked pull requests come first. `GET repos/{owner}/{repo}/pulls/{number}` carries a `stack` field for a member, `{ number, position, size, base: { ref, sha }, id }`, and has no such field for a PR in no stack. `GET repos/{owner}/{repo}/stacks/{number}` lists the members bottom to top in `pull_requests`, with `number`, `title`, `state`, `merged_at`, `draft`, `html_url` and head/base `ref`, `sha` and `repo` (`id`, `name`, API `url`; no `full_name`). GraphQL has the same data as `PullRequest.stack { number size baseRefName entries { position pullRequest } }`, but the view stays on REST GETs. GitHub has no web page for a stack; the stack is shown on each member’s PR page.

When the current PR has a `stack`, the view shows that stack’s members in GitHub’s order, top first, with their states and the current PR highlighted, down to the stack’s base branch. Each row ends with its position (“3 of 4”, 1 at the bottom), and the header has a step bar: one segment per position, left to right from the bottom, in the PR's state colour (draft dashed, positions beyond the 24 shown blank), with the current PR's segment ringed in the link color. The bar is `aria-hidden`, since every row already says its step and state. Branch stacks and unordered GitHub stacks have no positions, so neither appears. GitHub has no web page per stack, so the header's stack number is plain text. It makes no branch lookups then: every member of a GitHub stack can target the default branch, because GitHub moves the next PR onto the base whenever the one below it merges. The order is trusted only when the list agrees with the current PR’s own position and the stack’s size; otherwise the members are listed by number with a notice, without positions and without a rail joining them. A stack that cannot be loaded or read falls back to branch relationships with a notice, and never as a standalone PR.

## Branch stacks

Without a GitHub stack, relationships come from GitHub’s base/head repository, branch and commit metadata. A parent is confirmed only when one PR has the matching head commit in a complete lookup. Branch names, PR numbers, worktree creation order and text in PR descriptions do not establish stack order. A single dependent continues its parent's rail. Several dependents of one PR each get a rail of their own, set in under a “Depends on #” caption and joined to the parent's rail, so their display order does not imply dependencies between them. A chain ends at its root's base branch when that is confirmed; otherwise the end is dashed and shows the branch the root targets with why its parent is unknown (ambiguous candidates, unconfirmed, retargeted, or beyond the lookup limit).

Ambiguous parent candidates remain links outside the confirmed ordering. Missing or deleted metadata, partial GitHub responses, authentication/network failures and lookup limits are shown explicitly. Dependents inside a different fork repository are not searched.

A PR with no parent PR by branch has its issue events checked (`GET repos/{owner}/{repo}/issues/{number}/events`). A `base_ref_changed` or `automatic_base_change_succeeded` event means GitHub moved its base, by hand or when the PR below it merged. REST events do not name the previous branch, so the row says the PR it was stacked on could not be confirmed, and the view does not call it standalone. A merged PR with nothing found says that PRs stacked on it may have been retargeted when it merged: they no longer target its branch, and nothing in REST metadata leads from it to them. **Standalone** is kept for a PR that is not merged, has no GitHub stack, no parent or dependent by branch and no base change.

Loading is on demand, read-only and bounded to 24 shown PRs, 100 results per branch or event lookup and 60 API requests. A GitHub stack takes two requests; a larger one shows the 24 members around the current PR and says how many more are above and below. Review and check status per PR are left out: neither response carries them, and asking for them would cost one or two requests per PR (up to 48 more for 24 PRs). The Checks tab already shows the current PR's checks. Opening the view never restacks, rebases, pushes, publishes or merges anything.

## Panel integration contract

`PrStack` in `src/renderer/chat/pr-stack.js` follows the existing Checks module:

```js
import { PrStack, PR_STACK_TAB } from './pr-stack.js';

const prStack = new PrStack(sidePane, ctx, {
  list: (id) => api.contacts.prStack(id),
  open: (url) => api.app.openExternal(url),
});
```

`PR_STACK_TAB` is `pr-stack`. `chat/main.js` registers its picker entry, singleton restoration mapping, View/Code menus and PR-button handler. `chat.html` loads `styles/pr-stack.css`. The shared panel continues to own pin storage, order, explicit Close and unavailable placeholders. PR-stack registration checks for a working folder and excludes This computer; archived conversations retain this read-only view.

| Method      | Contract                                                                                                                                                               |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `kind`      | Picker descriptor `{ label, icon, open }`; `open` calls `show()`.                                                                                                      |
| `show()`    | Opens/selects the singleton tab and refreshes. Repeated selection coalesces an in-flight read.                                                                         |
| `changed()` | Call when the current contact or its PR metadata changes. Refreshes a visible tab; a same-contact change during loading invalidates that answer and queues a new read. |
| `close()`   | Invalidates pending answers. The pane invokes it through `onClose`; it does not itself remove the tab.                                                                 |

Contact/PR metadata changes and completed turns refresh a visible stack. A missing checkout invalidates pending reads and uses the shared unavailable-tab path. This registration preserves the existing archive cleanup, queue identity forwarding and Settings hooks.

The read request `contact:pr-stack` accepts only a contact ID. The main process resolves its folder and verified PR before asking GitHub. It adds no analytics event; opening the registered pane can use the existing tab-open count.
